# DECISIONS.md

1. **Indexes.** I created five indexes:
   - **`idx_emp_code_unique`** on `employees.emp_code` (unique): enforces the uniqueness constraint on employee codes and supports all lookups by `emp_code`. The unique index also handles the concurrent duplicate-create race (only one `insert_one` wins).
   - **`idx_empcode_date_unique`** on `attendance_logs.(emp_code, date)` (unique compound): enforces one record per employee per day and prevents concurrent duplicate punch-ins. Supports the `PATCH /attendance/{emp_code}/{date}` lookup and all analytics that filter by `emp_code` + `date` range.
   - **`idx_date_desc_empcode_asc`** on `attendance_logs.(date DESC, emp_code ASC)`: serves the `GET /attendance` list endpoint which sorts by date descending then emp_code ascending, and supports range queries on `date`.
   - **`idx_department`** on `employees.department`: speeds up department-filtered employee queries and analytics lookups.
   - **`idx_joined_on`** on `employees.joined_on`: supports headcount calculations that filter by `joined_on <= month_end`.
   - I considered a compound index on `attendance_logs.(emp_code, late_minutes, date)` for the late leaderboard, but rejected it because the `$lookup` join with employees already narrows the set, and the aggregation groups by `emp_code` regardless. The existing `(emp_code, date)` index covers the `$match` stage sufficiently.

2. **Punch-in race.** Two identical punch-in requests arrive simultaneously. Both compute the same `attendance_date` and try to insert a document with the same `(emp_code, date)`. Because of the unique compound index on `(emp_code, date)`, exactly one `insert_one` succeeds (returns 201) and the other raises `DuplicateKeyError`, which my code catches and returns 409. No check-then-insert pattern is used — the database enforces it atomically.

3. **Ties.** Two employees tied on late minutes at the cutoff: my leaderboard uses standard competition ranking (1, 2, 2, 4). I iterate through the sorted results and only increment the rank when the `total_late_minutes` value is strictly less than the previous entry's. Then I include every employee whose `rank <= limit`. This means if two employees tie at rank 10 with a limit of 10, both appear in the response — the response can contain more than `limit` rows.

4. **Headcount.** The department summary queries the `employees` collection with `joined_on <= month_last` (and optionally filters by department). This returns all employees who had joined by the end of the month, whether or not they have any attendance logs. The aggregation on `attendance_logs` is separate — it only computes metrics over records that exist. Employees with zero logs still count toward the headcount because headcount comes from the `employees` collection, not from `attendance_logs`.

5. **One thing I would change** at 100× scale: I would shard `attendance_logs` on `(emp_code, date)` and pre-aggregate daily department-level summaries into a separate `department_daily_stats` collection using a nightly batch job or change streams. The analytics endpoints would read from the pre-aggregated collection instead of scanning raw logs, reducing both latency and I/O. I would also add a read-replica set for analytics queries to avoid contending with punch-in/out writes.

6. **Department trend gap-filling with `$densify`.** The spec requires using a gap-filling stage rather than a Python loop. I use `$densify` on a BSON datetime field (`date_dt`, converted from the string `date` via `$dateFromString`) with a `step: 1, unit: "day"` range bounded by the requested `from`/`to` dates. This ensures exactly one row per calendar day is produced by MongoDB, including days with zero attendance records. After `$densify`, I fill null fields (present_count, late_count, date_str) with `$ifNull` and compute headcount and attendance_rate per-day in Python (because headcount depends on each employee's `joined_on` date, which varies per day and requires cross-referencing the employees collection). The 7-day moving average is also computed in Python since `$setWindowFields` doesn't support conditional null-excluding averaging the way R8 requires (mean of non-null rates only, with half-up rounding).
